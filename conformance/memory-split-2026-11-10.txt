What 40,000 element sets hold in GPKit, split: the propagators themselves against the input text and the records read
from it. It splits the 174 MB measured at 40,000 sets in benchmark-stream-2026-11-10.txt (the owner's ruling of
2026-11-10: measure first; propose a design only if the propagators dominate).
Run on 2026-11-10 (UTC), 16:55:27Z to 16:57Z, on a Mac17,4 (Apple M5, 16 GB), macOS 27.2.1 (26B131), Apple Swift
version 6.4.2, release build, branch v2-propagator-memory (GPKit 1.3.0 with v2-streaming). Each stage ran in a process of
its own, started only with the one-minute load at 12 or less, no xcodebuild and no simulator round. The load was
10.8 to 11.2. At 40,000 every stage ran twice; the runs agree to 0.1 MB except "all", 173.6 and 175.6 MB at the peak.

How it was run, one process a stage:

  swift run -c release --package-path tools/benchmark benchmark --count 40000 --memory STAGE

STAGE is one of:
- none: nothing made;
- text: the CSV text;
- file: the text and the file GPKit reads from it;
- all: the text, the file and the propagators, as the other benchmark modes keep them;
- sets-only: the element sets alone, read 1,000 at a time, so that no whole text or file is ever held;
- propagators-only: the propagators alone, made the same way.

Sizes in MB are MiB (1,048,576 bytes), as the tool prints them. "Most memory held" is the process's resident peak. "Footprint" is Darwin's phys_footprint at the end, with
everything the stage made still held: what the system counts against an app. The sets are the tool's made-up
constellation. A real provider file's names and keywords would differ in size per set [untested].

Sizes the compiler gives: Propagator 1,368 bytes, of which its ElementSet is 472 and the SGP4 state and gravity 896
(a Propagator holds its ElementSet as a value).

The split of the 174 MB at 40,000 sets (footprints less the 2.3 MB of an empty process; "all" is 145.2 MB of
footprint, its 174 MB peak including what parsing holds while it runs):

- the propagators, with the element sets they hold: 79.4 MB, 55 per cent. Of that:
  - the Propagator array, 52.2 MB: 34.2 MB of SGP4 state (40,000 × 896 bytes) and 18.0 MB of element sets held inline (40,000 × 472);
  - the element sets' own allocations, about 27 MB (sets-only's 45.1 MB less its 18.0 MB array), about 690 bytes a
    set. That figure includes what the allocator kept from reading 1,000 at a time [inferred: not split further].
- the input text, 13.6 MB, 9 per cent.
- the file read from it, the records and their own copies of the element sets: 79 MB of "file" less 13.6 MB of
  text; on top of the propagators in "all", 52 MB. That is 36 per cent.

Linear: the propagators alone are 22.3 MB at 10,000 sets and 79.4 MB at 40,000, 2.2 and 2.0 KB a set with these
made-up sets, a lower bound. A real capture of 11,141 sets gives about 3 KB a set (below).

The verdict, against the owner's test:
- The propagators are the largest part, 55 per cent of what "all" holds. They do not dominate it: the input text and
  the file are the other 45 per cent.
- That part goes away without any change to GPKit, by reading in pieces and keeping only the propagators, as
  propagators-only does: 87 MB at the peak against 174.
- So no design is proposed (the owner's rule).
- What remains, if a phone needs less than about 3 KB a set (real capture of 11,141 sets; about 2 KB made-up, a
  lower bound): the 896 bytes of SGP4 state, and the element set each
  propagator keeps (472 bytes inline and about 690 of its own). That is a question for the owner, not a design here.

The file is the largest element-set capture held privately: the maintainer's fetch of 2026-09-21, the supplemental GP
CSV of one large constellation, 11,141 element sets, all read, none refused. It was read in place, for this only, with
no request made. Nothing of it is kept here, and the tool prints no name or value from it. Beside it are 11,141
made-up sets, the same count. Each stage ran in a process of its own, twice, behind the same gate as above (load 8 to
11).

How it was run:

  swift run -c release --package-path tools/benchmark benchmark --memory STAGE --file PATH --format csv
  swift run -c release --package-path tools/benchmark benchmark --memory STAGE --count 11141

"pieces" is propagators-only under the name of the pattern it measures. It reads the file from the disk about 1,000
records at a time and keeps only the propagators. Before measuring, "--memory check-pieces" checked that the file read
in pieces gives the element sets it gives whole: 11,141, the same values in the same order. A planted fault, the last
short piece dropped, made it fail ("11000 sets against 11141", exit 1).

Bytes a set, less an empty process, from the means of the two runs:
- the propagators kept alone ("pieces"): 3.0 KB a set from the real file, 2.45 KB a set from made-up sets at the same
  count. At 40,000 made-up sets it is 2.1 KB, and the fixed part counts for less: a run at 17:18:43Z gave 83.3 MB of
  footprint and 88.7 MB at the peak.
- the element sets kept alone ("sets-only"): 1.98 KB a set from the real file, 1.41 KB from made-up sets.

So real data changes the figure: about 3 KB a set, not 2. The extra is about 0.57 KB a set, and it is in the element
sets' own allocations. The SGP4 state and the 1,368-byte Propagator are the same. A supplemental GP CSV carries more
columns than the made-up sets, which GPKit keeps in each set's otherKeywords, and longer names and ids. That this is
where the extra comes from is [inferred: not split further]. A plain GP file of the same objects might sit between
the two [untested].

The made-up result stands for what it measured. The catalogue-scale article now gives both figures.

The array made at its full size matters. In a first pass the pieces stages let the array of propagators grow by
doubling ("--unreserved" now). The real file's "pieces" then held 54.0 MB (59.4 MB at the peak), against 34.2 MB made
at full size. That is close to the 61 MB peak of reading the whole file, so most of the pattern's saving was undone.
The tool now counts a file's records first, a line at a time, and makes the array at that size. The article says to
do the same.
